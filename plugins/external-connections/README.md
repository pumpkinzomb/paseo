# External connections

Built-in host-scoped remote MCP registry. Configure trusted HTTPS servers (or a loopback HTTP bridge) under Plugins → External connections. Configuration is opt-in and defaults disabled; Codex and Claude provider selection is explicit. Both lead and child interactive agents receive the selected servers when a new provider process opens. History-only opens receive none. No existing session is restarted by saving.

This is a connection framework, not a Google connector. Google Docs, Sheets and Gmail need a separately configured trusted MCP bridge and its own OAuth consent, scopes and token lifecycle. The registry does not copy ChatGPT/Claude connections, perform OAuth, test server health, store credentials or advertise read-only enforcement. Endpoint credentials, query strings and fragments are rejected; secrets must be managed by the external bridge. A configured/enabled row does not prove authentication or connectivity. Provider approval policies still apply to tool calls.

Settings updates take effect at the next agent process open. Disabling/removing an entry does not revoke remote OAuth permissions or detach tools from an already running process; end/reopen affected sessions and revoke permissions at the service when required.

## Google connection UI and host service boundary

The Google card is separate from generic endpoint registration. Its default state is **setup required**, not connected. No OAuth request, Keychain access or remote data request occurs on screen load. The typed Google RPC facade requires the daemon's existing `daemon.manage` permission and returns only public status/scopes or a validated Google authorization URL. Errors are fixed codes, not raw adapter responses. Reading scopes is not a connectivity probe.

`registerGoogleConnectionRpc(server, service)` accepts a trusted host-owned `GoogleConnectionService`. The current built-in registration deliberately supplies no service until OAuth client configuration and a secure credential store are wired and verified. A future service must own PKCE/callback state, cancel-versus-exchange coordination, secure token storage, per-agent bridge capability issuance, and revoke live bridge capabilities before resolving `forget()`. It must not save OAuth tokens in plugin settings or pass Google tokens to model providers. The narrow adapter may pass a short-lived bridge bearer through runtime MCP headers only.

Documents/Sheets write scopes are separate explicit opt-ins; Gmail sending is not offered. Local disconnect does not imply remote Google grant revocation. Existing provider processes may retain stale MCP configuration, but their bridge credentials must no longer authorize requests after local disconnect. Google setup is not complete merely because this UI and RPC facade exist.

The built-in now receives daemon-owned `stateDirectory`, fixed `pluginDirectory`, and a runtime mode selected from the desktop launcher's existing `PASEO_NODE_ENV` marker. Missing/unknown mode defaults to packaged, never development fallback. Only the trusted built-in receives this context. Google host modules are loaded directly from that fixed directory so helper-source URLs survive plugin bundling. Missing modules or unavailable storage remain setup-required. `google.configure` is an explicit UI action: client ID is public configuration, client secret is transient input to native storage, never plugin settings. Configuration is not authorization. The request uses the existing privileged `daemon.manage` channel and controller errors never include inputs.

After successful user OAuth consent, only Codex/Claude interactive provider launches receive `paseo-google` with a validated loopback endpoint and session bearer header. History reads receive none. Provider-process close disposes that agent's capability. Long-lived Google credentials never enter provider configuration. The bridge's capability lifetime and reconnect limitations are defined by the host service; no automatic renewal is claimed here.
